## 1. V1 · sqlite-vec（Windows / Py3.13）—— ✅ 通过

**验证内容与结果**（5 万条 1024 维向量，设计规模上限）：

| 验证项 | 结果 | 结论 |
|---|---|---|
| 扩展加载 | `pip install sqlite-vec` + `sqlite_vec.load(conn)` 正常 | 兼容 Py3.13，无需额外编译 |
| vec0 建表 | dim=1024 建表 0.3ms | 与 `chunk_vec` 设计一致 |
| 批量写入 | 5 万条 29.3s（约 1700 条/秒） | 全量重建（笔记+手册规模）分钟级，可接受 |
| KNN 检索 | top-10（含回表 + `status='ready'` 过滤）**中位 33.8ms / 最大 35ms** | 远低于交互可感知阈值（~500ms），达标 |
| 删除 | 100 条 6ms | FR-RAG-10 删除清理无压力 |
| 维度切换 | DROP + 重建空表 8.9ms | R4 结论：模型切换需全量重嵌入重建，成本可接受 |

**结论**：全 SQLite 方案（D3）成立，**无需备选 Chroma**。框架中的降级逻辑（加载失败仅告警）保留为安全网。

**对实现的影响**：
1. `chunk_vec` 建表维度以 `embedding.dim` 配置为准——首次配置 embedding 后建库，切换模型 → 提示重建（已在 03 设计 R4 落实）；
2. 检索 SQL 采用 KNN + JOIN 回表 + WHERE 过滤形态（`embedding MATCH ? AND k = ?`），范围过滤在规模内性能足够（database-rules 第 11.3 节方案验证成立）。

## 2. V2 · FTS5 中文分词 —— ✅ 通过（方案：应用层 bigram + 短语查询）

**500 篇模拟售后笔记（含型号 ACS-2600i/GK-800、故障码 ERR-1204/E-0301、中文现象描述）对照结果**：

| 查询用例 | 默认 unicode61 | bigram + 短语 |
|---|---|---|
| 型号精确（ACS-2600i） | 74 命中 | 74 命中 |
| 故障码（ERR-1204 / E-0301） | 117 / 108 | 117 / 108 |
| 中文词（无法启动 / 传感器） | **0 / 0** | 90 / 155 |
| 中文短语跨词（压力不足） | **0** | 96 |
| 客户名（客户15厂，期望 17） | 17 | **17（精确）** |
| 检索延迟 | — | 中位 0.01ms |

**结论**：
1. **默认 unicode61 不可用**（中文词 0 命中），确认采用 **应用层 bigram**（database-rules 第 10 节默认方案成立）；
2. 型号/故障码在两种方案下均精确命中（ASCII 连续串原样保留），混合检索的关键词侧满足 FR-RAG-16；
3. 分词器切换只需重建 `chunk_fts` 表（规则第 10 节预留路径验证成立），后续如换 jieba 等仅重索引。

**Spike 过程中发现的关键实现约束（已验证并写入结论）**：
1. **分词必须保持原文 token 顺序**——初版按「先 ASCII 后 CJK」分组扫描会打乱顺序，导致 FTS5 短语邻接匹配失效（`客户15厂` 短语 0 命中）；改为按原文顺序切分后精确命中 17；
2. **查询侧必须用短语表达式**——多 token 独立 AND 会过匹配（`客户15厂` AND 语义曾命中 33 行），连续查询段应合并为单个短语 `"tok1 tok2 ..."`；ASCII 串中的 `-` 在 MATCH 语法中是特殊字符，token 必须加双引号；
3. 参考实现：`backend/tests/spike_v2_fts.py` 的 `bigram_tokens()`（写入侧）与 `phrase_expr()`（查询侧），索引服务实现时**直接采用**。
