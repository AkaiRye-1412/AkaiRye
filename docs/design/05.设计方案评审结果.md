## 1. 评审范围与方法

1. **完备性**：四份设计文档是否覆盖需求文档 v1.1 的全部 FR/NFR 条目与原型交互（01 覆盖模块层，02 覆盖架构层，03 覆盖数据层，04 覆盖接口层）；
2. **一致性**：四方交叉核对——模块清单（01）↔ 前后端落点（02）↔ 表结构（03）↔ 端点/事件（04）；同时核对设计文档对两份规则文件的章节引用；
3. **决策闭环**：Q-01 ~ Q-14 的确认结论是否在后续文档中如实落地、有无被后阶段推翻或遗漏；
4. **可执行性**：设计粒度是否足以支撑开发计划与工程实现（不含代码级细节，符合各阶段范围约定）。

## 2. 设计矛盾（1 项，交互确认后整改）

### Q-15 · 「未入库」PDF 在 manual 表中如何表达【已确认 · 2026-11-25】

- **矛盾描述**：
  - 《01》M9 要求展示"未入库"文件并提供一键入库（FR-RAG-11）；
  - 《03》`manual.status` CHECK 枚举仅 7 态（queue/parsing/rebuilding/ready/failed/update/invalid），**无任何状态表示"扫描发现但从未入库"**；
  - 《04》`GET /api/pdf/tree` 称"扫描结果与 manual 表同步"，且 C2 阅读器统一按 `manual_id` 访问（`GET /api/reader/pdf/{manual_id}`）——若未入库文件无 manual 行，该端点无法服务 M9 的未入库预览（Q-04 结论）。
- **候选方案**：A. 扫描发现的 PDF 一律建 manual 行，状态机新增 `discovered` 初态；B. manual 只记录已触发过入库的手册，未入库文件由扫描实时合并返回（C2 需新增按路径访问端点）。
- **确认结论**：**采纳选项 A**——manual 表作为 pdf_root 的全量派生镜像，所有 PDF 统一有 `id`；M9 筛选纯 SQL、C2 双模式统一按 manual_id 访问、04 无需新增端点。
- **整改落点**：
  - 《03》v1.1：`manual.status` CHECK 扩为 **8 态**（首位 `discovered`）；第 3.3 节 manual 表增加 Q-15 结论说明；第 4 章一致性场景表新增"扫描发现新文件 → 建 manual 行 status='discovered'"；
  - 《04》v0.2：`/api/pdf/tree` 说明改为"扫描发现的文件一律建/同步 manual 行（新文件 status='discovered'）"；`GET /api/manuals` 与 `manual.updated` 事件的枚举描述对齐为 8 态；
  - 《api-rules》v1.1：枚举一致性条款对齐 8 态。
