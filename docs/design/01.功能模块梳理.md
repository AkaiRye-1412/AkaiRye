## 1. 文档目的

在进入技术方案、数据库与 API 设计之前，先完成一次"自上而下"的功能模块梳理，确保：

1. 项目的主要功能被完整识别，不漏项、不增项；
2. 模块边界清晰，职责不重叠；
3. 模块之间的依赖与数据流向明确；
4. 核心业务流程在模块层面跑通；
5. 原型与需求文档之间的差异被显式标记，避免后续设计阶段"按推断推进"。

本文件是后续技术方案、数据库设计、API 设计的输入，不替代任一前者。

## 2. 项目定位与边界（摘自需求文档）

### 2.1 定位

> 单人、本机优先的售后工作台：以网页界面呈现，由本地后台服务提供文件、索引、解析、终端等能力；围绕"客户 → 项目 → 售后记录"主线，提供看板、RAG 检索、笔记、终端、Git 状态等能力。

### 2.2 关键边界

| 维度 | 结论 |
|---|---|
| 用户 | 单用户（项目所有者本人），无账号、无权限、无多租户 |
| 部署 | 项目所有者本人的 Windows 机器；后台仅监听本机回环地址 |
| 数据源 | Obsidian vault 为业务数据唯一真相源；索引/向量库为可重建的派生数据 |
| 外部能力 | 云端 LLM（可配置）、云端 Embedding（已接受隐私代价）、本地 MinerU 解析 PDF、本地 Git 只读、本地 PTY 终端 |
| 非目标 | 不做多人协作、远程访问、完整工单、完整 IDE、自动重构 vault |

### 2.3 分期范围（用于模块优先级标注）

| 阶段 | 范围概述 | 对应优先级 |
|---|---|---|
| 一期 · 核心闭环 | 后台骨架 + 首页 + 售后笔记读写 + 项目列表 + 基础看板 + RAG（仅覆盖笔记）+ 模型配置 | P0 |
| 二期 · 手册链路 | PDF 入库 + MinerU 解析 + 内置阅读器 + 品牌筛选/对比 + 混合检索 | P1 |
| 三期 · 效率工具 | 多标签终端 + Git 只读 + 存量整理 + 高级看板 + 打包/托盘/自启 | P2 |

> **分期调整记录（2026-11-25）**：经项目所有者确认（见《02.整体架构设计.md》决策 D13），原一期（P0）与二期（P1）**合并为本次交付范围**，同步开发、一次性交付；三期（P2）不变。本调整**不改变功能范围与需求基线 v1.1**——上文 P0/P1/P2 为需求优先级标注，保持原样；仅开发排期变更，详见 02 文档。

> 模块梳理本身不区分阶段，但每个模块下会标注其功能项的优先级，便于后续排期。

## 4. 各功能模块详细梳理

### M1 · 首页台面

**对应需求**：FR-HOME-01 ~ 07、FR-DASH-01 ~ 08、FR-PROJ-01 ~ 05
**原型页面**：`首页`（views-home.js）

#### 4.1.1 职责

把"进行中项目、数据看板、全局提问、终端/新建笔记快捷入口、代码仓库折叠区"集中到一个入口页，做到"打开工作台即可看到当前售后全貌"。

#### 4.1.2 主要功能

| 子功能 | 说明 | 需求编号 | 优先级 |
|---|---|---|---|
| 顶部操作栏 | 全局提问框（回车唤起 RAG 面板并执行）+ 终端入口 + 新建笔记入口 | FR-HOME-02 / 03 | P0 |
| 进行中项目列表 | 扫描笔记生成；按客户分组；组内按最近更新倒序；显示状态、最近更新时间；支持"进行中 / 已归档"切换；待跟进项目置顶提醒 | FR-HOME-04 / FR-PROJ-01~04 | P0 |
| 数据看板 | 售后进度（进行中/已归档/待跟进数量）、记录趋势（近 8 周/近 6 月）、客户分布 Top N、时效（超阈值项目、平均处理天数）；时间范围切换（本月/近 30 天/近 6 月）；全部由扫描笔记头部字段计算 | FR-HOME-05 / FR-DASH-01~07 | P0 |
| 项目详情入口 | 从项目列表点击直接打开对应笔记 | FR-PROJ-05 | P0 |
| 代码仓库区 | 默认折叠；展示置顶仓库的 Git 状态 | FR-HOME-06 | P2 |
| 最近打开/检索 | 一期不做；作为三期可选增强 | FR-HOME-07 | P2 |

#### 4.1.3 职责边界

- **不维护项目档案**：项目列表完全由扫描笔记生成（FR-PROJ-01 / FR-PROJ-04），首页只负责"呈现 + 跳转"；
- **不混入 Git 指标**：Git 状态独立置于代码仓库区，不进售后看板（FR-DASH-08）；
- **不依赖实时全量扫描**：首页与看板加载应基于缓存 + 增量更新（NFR-PERF-04）。

### M2 · 售后笔记

**对应需求**：FR-NOTE-01 ~ 11、FR-PROJ-01 ~ 05
**原型页面**：`笔记`（views-notes.js）+ 笔记编辑器（弹层 / 内嵌）

#### 4.2.1 职责

直接读写 Obsidian vault 中"客户售后问题"文件夹下的 `.md` 文件，承载售后记录的"写、改、查、新建、归档"全过程；不建立第二份数据副本。

#### 4.2.2 主要功能

| 子功能 | 说明 | 需求编号 | 优先级 |
|---|---|---|---|
| 笔记列表 | 售后笔记列表；按客户分组；组内按最近更新倒序；支持"全部 / 进行中 / 已归档"筛选；关键词搜索（项目、客户、标签） | FR-NOTE-07 / FR-PROJ-02 | P0 |
| 直接读写 vault | 工作台直接读写同一份 `.md`，不建立副本 | FR-NOTE-01 | P0 |
| 新建笔记落盘 | 新建笔记写入现有"客户售后问题"文件夹；自动带出固定头部骨架与日期小节格式 | FR-NOTE-02 / 10 | P0 |
| 结构化头部 | 头部字段：客户（沿用 frontmatter `name`）、项目名、状态、开始日期、最近更新；编辑器可直接改客户/项目名/状态/开始日期（PATCH `/api/notes/{path}/meta`），只写 frontmatter 不动正文 | FR-NOTE-03 / 11 | P0 |
| 正文自由 | 正文为自由 Markdown；建议按"日期 + 问题标题"分小节记录 | FR-NOTE-04 / 08 | P0 |
| 一项目一笔记 | 一个项目一份主笔记，后续按日期小节续写，不拆分多份 | FR-NOTE-08 | P0 |
| 冲突处理 | 文件被外部修改且工作台有未保存内容时，保存前提示：重新加载 / 用我的覆盖 / 另存副本；禁止静默覆盖 | FR-NOTE-05 | P0 |
| 文件监听 | 监听 vault 变化；外部修改后工作台自动刷新并触发索引更新 | FR-NOTE-06 | P0 |
| 状态与归档 | 状态仅"进行中 / 已归档"；归档完全由用户手动触发，不自动归档 | FR-NOTE-09 | P0 |
| 客户/项目标识 | 客户沿用现有 frontmatter `name` 字段；项目名写入头部字段 | FR-NOTE-11 | P0 |
| 删除笔记 | 列表行悬停出现删除入口，二次确认后执行；**软删除**——文件移入 `{vault_root}/.trash/`（Obsidian 回收目录）而非物理抹除，拖回原目录即还原；列表、索引与 RAG 块引用同步清理 | FR-NOTE-12 | P0 |

#### 4.2.3 职责边界

- **不重排 vault 结构**：保持现有 Obsidian 目录结构（FR-NOTE-07）；
- **不重复录入**：不为已有笔记项目再建一份档案（FR-PROJ-04）；
- **不强制正文格式**：仅约束头部字段，正文为自由 Markdown（FR-NOTE-04）；
- **不自动归档**：归档完全手动（FR-NOTE-09 / OQ-07）。

#### 4.2.4 两种笔记形态（实现口径）

| 形态 | 判定 | 头部字段 | 列表展示 | 新建 |
|---|---|---|---|---|
| 项目笔记 | 有 `project` 或 `start_date` | name / project / status / start_date / updated | 项目名 + 摘要 | `客户-项目名.md` + 固定骨架 |
| 按日卡片 | 其余（真实 vault 现状：`75 Journal/售后卡片/YYYYMMDD.md`） | name / time / tags / description / title | 正文 H1（无则日期）+ description 摘要 + tags | 暂沿用项目笔记模板（卡片模板待确认） |

- 卡片缺 `status` 时按「进行中」统计，归档动作由服务层补写 `status` 键；
- 卡片不判「缺头」（`head_ok` 只要求 `name`），避免真实数据被整片标脏；

### M3 · 知识库与 RAG

**对应需求**：FR-RAG-01 ~ 27
**原型页面**：`知识库`（views-kb.js）+ 右侧 RAG 常驻面板（rag.js）

#### 4.3.1 职责

对笔记与手册建立索引（切块 + 向量化），提供基于混合检索的 RAG 问答，回答必须可溯源；管理 PDF 入库队列与索引状态。

#### 4.3.2 主要功能

按职责进一步拆为三个子模块：

#### (1) 索引入库子模块

| 子功能 | 说明 | 需求编号 | 优先级 |
|---|---|---|---|
| 笔记自动索引 | 对白名单文件夹中的笔记自动建立索引，无需手动触发 | FR-RAG-01 | P0 |
| 索引白名单 | 一期仅"客户售后问题"文件夹；白名单可配置、可扩展 | FR-RAG-02 / OQ-01 | P0 |
| 索引白名单可视化管理 | 在 M3 知识库页面内提供 vault 笔记浏览 + 勾选纳入/移出知识库的交互（合并自原型「所有笔记」页面，Q-01 已确认）；一期白名单严格限制为"客户售后问题" | FR-RAG-02 / FR-CFG-04（衍生） | P0（一期仅售后文件夹）/ 二期可扩展 |
| 增量更新 | 笔记保存后延迟 8 秒（可配置）自动增量；仅重建变化文件；失败有限次重试 | FR-RAG-03 / OQ-11 | P0 |
| PDF 手动入库 | 拖拽或勾选 PDF 触发入库；不做全量自动入库；入库触发入口在 M9 PDF 手册浏览与 M3 知识库均可提供 | FR-RAG-04 | P1 |
| PDF 解析 | 本地 MinerU 解析；结果为结构化文本/章节 | FR-RAG-05 | P1 |
| 章节切块 | 按章节/标题切块，保留标题层级；每块保留手册名、章节、页码等来源信息 | FR-RAG-06 | P1 |
| 向量化 | 切块内容发送至云端 embedding 并写入向量库 | FR-RAG-07 | P1 |
| 入库队列 | 入库任务排队执行；状态：排队/解析中/已入库/失败；失败可见可重试；队列管理归 M3 | FR-RAG-08 | P1 |
| 引用原文件 | 入库仅记录 PDF 原路径，不复制；移动/改名后标记失效并提供"重新定位"（重新定位操作归 M3） | FR-RAG-09 | P1 |
| 删除/更新 | 删除 PDF 清理切块与向量；内容变化标记"有更新"，由用户选择立即重建/稍后/忽略；重建期间保留旧索引；移动只标路径失效（操作归 M3） | FR-RAG-10 / OQ-12 | P1 |
| 未入库不检索 | 未完成入库的 PDF 不参与检索，仅显示在待入库列表 | FR-RAG-11 | P1 |
| 手册元数据 | 不强制填写厂家/型号；品牌能从路径/文件名识别时自动打标 | FR-RAG-12 | P1 |
| 品牌枚举 | 固定枚举：高创 / ACS / Agito；可配置新增；不做自由文本输入 | FR-RAG-13 | P1 |
| 图片/照片 | 一期不索引；二期可选仅对售后文件夹图片做 OCR；不做图像理解 | FR-RAG-14 / OQ-04 | P2 |
| 文档格式 | 初期仅 PDF（含扫描版）；Word/Excel/PPT 暂不支持 | FR-RAG-15 / OQ-02 | P1 |

#### (2) 检索呈现子模块（与 C1 RAG 面板共用界面）

## 6. 核心业务流程

### 6.1 售后记录生命周期

```
新建笔记（M2，模板带出头部骨架）
   │
   ▼
填写头部字段（客户=frontmatter name / 项目名 / 状态=进行中 / 开始日期）
   │
   ▼
按日期小节续写正文（自由 Markdown）
   │
   ▼
保存落盘（M2 直接写 vault，不建副本）
   │
   ├─► M1 首页/看板：扫描头部字段 → 进行中列表 + 看板数字更新
   │
   └─► M3 知识库：8 秒防抖 → 增量索引 → 可被 RAG 检索
   │
   ▼
（处理完成）用户手动归档
   │
   ▼
```

## 8. 待确认问题

> 以下问题均为「原型中已存在 / 表述存在差异 / 需求文档未明确覆盖」的项；本设计文档**不**将其作为既定事实陈述，等待项目所有者确认后再纳入下一阶段设计。

### Q-01 · 「所有笔记」页面是否作为独立功能模块纳入？【已确认 · 2026-11-25】

- **背景**：原型导航中存在独立的「所有笔记」入口（`views-allnotes.js`），用于浏览 Obsidian vault 中**所有** `.md` 文件（含"客户售后问题"文件夹之外的其他笔记），并提供：
  - 按 vault 原目录树折叠浏览；
  - 关键词搜索（标题 + 正文高亮）；
  - 三态勾选纳入/移出知识库（文件夹级 + 文件级 + 排除）；
  - 全部/已勾选/未勾选筛选；
  - 点击只读阅读；
  - 概览统计与当前知识库来源 chips。
- **与需求文档的差异**：需求文档 FR-NOTE / FR-RAG-02 仅明确"售后笔记"（即"客户售后问题"文件夹下的笔记）作为业务实体和索引白名单；未将"vault 全量笔记浏览"列为独立功能模块。
- **确认结论**：**采纳选项 B —— 不作为独立模块，原型功能合并入 M3 知识库页面，作为索引白名单的可视化管理入口**。
  - 一期白名单严格限制为「客户售后问题」文件夹，避免索引范围蔓延与云端 embedding 费用不可控；
  - 「vault 全量浏览 + 精细勾选」作为 M3 知识库页面内的索引管理子功能呈现，不引入与 M2 售后笔记列表定位重叠的第二个笔记浏览入口；
  - 后续若需扩展白名单到其他文件夹，通过 M3 的可视化管理入口操作，仍归 M3 职责。
- **对模块划分的影响**：不新增「M9 · Vault 笔记浏览」模块；M3 知识库与 RAG 模块新增子功能「索引白名单可视化管理」（纳入"哪些文件夹/文件进索引"的浏览与勾选交互）。

### Q-02 · RAG 常驻面板的常驻范围？【已确认 · 2026-11-25】

- **背景**：需求文档 FR-HOME-01 描述首页布局为"右侧 RAG 面板"；FR-RAG-19 说"RAG 助手以常驻右侧面板呈现"。原型实现中，**所有页面**（首页、笔记、知识库、终端、代码仓库、设置、存量整理、PDF 手册、所有笔记）右侧都有 RAG 面板。
- **与需求文档的差异**：需求文档未明确说明 RAG 面板是否在所有页面常驻，还是仅在首页常驻。
- **确认结论**：**采纳选项 A —— 所有页面常驻（与原型一致）**。
  - RAG 面板作为**全局常驻组件**，所有页面共享同一面板实例、状态与上下文；
  - 支持 FR-RAG-18 自动感知当前打开笔记所属客户/项目；
  - 支持"边写边问"核心场景（编辑笔记时可同时提问）；
  - 仍保留可拖宽、可折叠、可全屏、宽屏默认展开/窄屏默认折叠的交互。
- **对模块划分的影响**：C1 RAG 常驻面板明确为"全局常驻组件"，在所有页面挂载；前端架构需保证面板状态（当前会话、范围、上下文）跨页面一致。

### Q-03 · 「PDF 手册」页面是否作为独立功能模块纳入？【已确认 · 2026-11-25】

- **背景**：原型导航中存在独立的「PDF 手册」入口（`views-pdf.js`），用于浏览配置的本地 PDF 根目录下的所有 PDF（含未入库），并提供：
  - 按文件夹分组折叠（高创 / ACS / Agito / 其他 / 未分类）；
  - 搜索 / 品牌 / 状态筛选；
  - 点击文件在页面右侧内嵌预览（复用 reader 组件）；
  - 未入库文件一键加入知识库；
  - 失效引用提示、重新扫描。
- **与需求文档的差异**：需求文档 FR-RAG-04 ~ 15 描述了 PDF 入库的**能力**，但未明确将其作为独立导航页面；入库相关交互在原型中同时出现在「知识库」页面（入库队列、状态、重试、重建、重新定位、删除清理）和「PDF 手册」页面（浏览 + 一键入库）。
- **确认结论**：**采纳选项 A —— 作为独立模块 M9「PDF 手册浏览」纳入；与 M3 知识库分工明确**：
  - **M9 PDF 手册浏览**：浏览 PDF 根目录、分组/筛选/预览、一键入库触发、失效引用提示、重新扫描、品牌自动识别；
  - **M3 知识库**：入库队列管理、状态推进、重试、重建、重新定位、删除清理、索引白名单可视化管理（合并自原型「所有笔记」，见 Q-01）；
  - 两模块通过入库任务状态协作：M9 触发 → M3 接管队列 → M9 通过状态筛选查看进度。
- **对模块划分的影响**：新增「M9 · PDF 手册浏览」模块；二期范围纳入该模块；M3 与 M9 的职责边界已在 4.3.3 与 4.9.3 中明确。

### Q-04 · 内置 PDF 阅读器（M4 / C2）的复用边界？【已确认 · 2026-11-25】

- **背景**：原型中 `reader.js` 同时承担：
  - 从 RAG 来源角标打开 PDF 并跳页高亮（FR-RAG-24）；
  - 从「PDF 手册」页面点击未入库 PDF 进行本地预览（不依赖入库）。
- **与需求文档的差异**：需求文档 FR-RAG-24 只描述了"来源跳转"用途，未明确"未入库 PDF 预览"用途。
- **确认结论**：**采纳选项 A —— 阅读器同时承担两种用途（与原型一致）**。
  - C2 PDF 阅读器组件作为**统一 PDF 呈现层**，同时服务：
    - C1 RAG 面板的来源跳转（跳页 + 高亮，依赖入库时记录的页码等来源信息）；
    - M9 PDF 手册页面的未入库 PDF 预览（不依赖入库，直接打开原路径文件）；
  - 二者共享同一组件实例、多标签状态与并排对比能力，保证交互一致；
  - 阅读器需同时支持"已入库 PDF（带来源元数据跳转）"与"未入库 PDF（仅本地预览）"两种打开模式。
- **对模块划分的影响**：M4 / C2 的职责边界扩展为"统一 PDF 呈现层"；M9 的文件预览明确依赖 C2；前端架构需保证阅读器实例在跨调用方（C1 / M9）下的一致性。

### Q-05 · 索引选择的粒度？【已确认 · 2026-11-25】

- **背景**：需求文档 FR-RAG-02 / FR-CFG-04 表述为"索引白名单（文件夹级）"；原型 `views-allnotes.js` 实现了更精细的索引选择：文件夹纳入 + 文件级纳入 + 文件夹排除 + 文件排除（`indexSelection: folders / files / excludedFiles / excludedFolders`），支持"最具体的目录规则生效"。
- **与需求文档的差异**：需求文档仅约束到"白名单文件夹"粒度，原型已细化到"文件夹 + 文件 + 排除"。
- **确认结论**：**采纳选项 C —— 一期文件夹级白名单，二期再引入精细粒度**。
  - **一期**：严格按需求文档"文件夹级白名单"，白名单仅"客户售后问题"单一文件夹；M3 知识库页面的索引白名单可视化管理仅提供文件夹级勾选；
  - **二期**：演进到原型精细粒度（文件夹纳入 + 文件级纳入 + 文件夹排除 + 文件排除 + 最具体规则生效），届时 M3 白名单可视化管理 UI 扩展支持文件级勾选与排除规则；
  - 二期演进的价值前提：白名单已扩展到多个文件夹（如把"工作笔记""学习笔记"等纳入），文件夹级粒度不足以表达"纳入某文件夹但排除其中某些文件"的需求。
- **对模块划分的影响**：一期 M3「索引白名单可视化管理」子功能按文件夹级实现；二期扩展为精细粒度；数据模型设计阶段需预留精细粒度的扩展空间（避免一期数据结构无法演进）。

### Q-06 · 看板时间范围与聚合粒度？【已确认 · 2026-11-25】

- **背景**：需求文档 FR-DASH-05：「默认本月；可切换近 30 天 / 近 6 月」；原型 `views-home.js` 中 `trendFor` 实现了 `month`（本月·按周）/ `30d`（近 5 周·按周）/ `6m`（近 6 月·按月）三档。
- **一致性**：基本一致，仅"近 30 天"在原型中呈现为"近 5 周·按周"，二者语义近似但不完全等同。
- **确认结论**：**采纳选项 A —— 严格按需求文档**。
  - 看板时间范围严格按 FR-DASH-05：「本月 / 近 30 天 / 近 6 月」三档；
  - **聚合粒度（按日/周/月）留给设计阶段决定**，不在功能梳理阶段过早约束；
  - **FR-DASH-02 的"近 8 周"保留为需求文档基线**，与 FR-DASH-05 的"近 30 天"并存：
    - FR-DASH-05 是看板顶部的时间范围切换器（用户可切换三档）；
    - FR-DASH-02 是趋势统计的口径描述（"按周/月统计，近 8 周 / 近 6 月"）；
    - 设计阶段需调和二者：可能在"近 30 天"档内默认按周聚合（约 4-5 周），并在趋势图旁提供"近 8 周"作为可选扩展视图；具体调和方式在设计阶段确定。
- **对模块划分的影响**：M1 看板的时间范围切换按 FR-DASH-05 三档；聚合粒度与"近 8 周"视图的具体呈现留待设计阶段。

### Q-07 · 终端「后台异常恢复」的提示形式？【已确认 · 2026-11-25】

- **背景**：NFR-DATA-04 明确"后台异常退出后，重启可恢复索引状态；**终端会话允许丢失**（需提示）"。原型中终端会话通过 `localStorage` 持久化（模拟），未展示"后台异常导致终端丢失"的提示形态。
- **确认结论**：**采纳选项 A —— 全局 toast 提示**。
  - 启动时检测到上次后台异常退出 → 全局 toast 提示"终端会话已丢失"；
  - 符合 NFR-DATA-04"需提示"的要求；
  - 提示为非阻塞 toast，用户可关闭；
  - 索引状态按 NFR-DATA-04 正常恢复（不影响索引）。
- **对模块划分的影响**：M5 终端的异常恢复 UX 明确为"全局 toast 提示"；M8 系统设置不涉及（OQ-10 已明确不备份终端会话）；属于三期（P2）实现细节，具体提示文案与触发条件在设计阶段再细化。

### Q-08 · 「在此目录打开终端」（FR-TERM-06）的入口范围？【已确认 · 2026-11-25】

- **背景**：FR-TERM-06 说"从项目/仓库处可'在此目录打开终端'"。原型中代码仓库页（M6）有该入口；但"项目"（M2 售后笔记）是否需要该入口、以及对应目录是什么（笔记文件所在 vault 路径？还是项目代码仓库路径？）并不明确。
- **确认结论**：**采纳选项 A —— 仅 M6 代码仓库提供「在此目录打开终端」入口**。
  - **M2 售后笔记不提供该入口**：售后笔记目录是 vault 内"客户售后问题"子目录，在此打开终端的实际价值有限；
  - **FR-TERM-06 的"项目"理解为"代码项目（仓库）"**，而非"售后笔记项目"；
  - **入口位置**：M6 代码仓库页面（每个仓库行提供"在此目录打开终端"按钮）；
  - **M5 终端接收**：M5 终端接收仓库路径作为新标签的初始工作目录（与 FR-TERM-05「独立工作目录」一致）。
- **对模块划分的影响**：M2 与 M5 之间无"在此目录打开终端"协作；M6 与 M5 之间通过仓库路径协作；FR-TERM-06 的入口范围明确限定在 M6。

## 9. 设计结论摘要（待审核）

### 9.1 主要设计结论

1. **模块划分**：项目划分为 **10 个一级功能模块 + 2 个常驻组件**（M1 首页台面 / M2 售后笔记 / M3 知识库与 RAG / M4 内置 PDF 阅读器 / M5 终端 / M6 代码仓库 / M7 存量笔记整理 / M8 系统设置 / **M9 PDF 手册浏览** + C1 RAG 常驻面板 / C2 PDF 阅读器组件）；其中 M4 与 C2 在原型中是同一实现，设计阶段可合并表达。M9 为 Q-03 确认后新增。
2. **数据主线**：以 Obsidian vault 为唯一真相源，业务层级为「客户 → 项目 → 售后记录（一份主笔记按日期小节续写）」；索引/向量库为可重建的派生数据；PDF 入库仅引用原路径、不复制。
3. **模块关系**：M2 售后笔记是数据源头，M1 首页/看板与 M3 知识库都依赖扫描笔记；C1 RAG 面板依赖 M3 索引并跳转至 M2/M4；M9 PDF 手册浏览触发入库 → M3 知识库接管队列管理；C2 PDF 阅读器同时服务 C1 来源跳转与 M9 未入库预览（Q-04）；M8 系统设置横切所有模块。
4. **核心业务流程**已梳理 6 条：售后记录生命周期、笔记索引流程、PDF 入库流程、RAG 问答流程、存量整理流程、文件冲突处理流程。
5. **分期对齐**：模块梳理不区分阶段，但每个子功能均标注了优先级（P0/P1/P2），与需求文档第 8 章一致：一期核心闭环（首页 + 笔记 + 项目 + 看板 + 笔记 RAG + 模型配置）、二期手册链路（PDF + MinerU + 阅读器 + 对比 + 混合检索）、三期效率工具（终端 + Git + 存量整理 + 打包）。
