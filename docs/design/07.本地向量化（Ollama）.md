# 07 · 本地向量化（Ollama）

> 2026-11-28 落地。向量化从云端（火山 doubao-embedding-vision，2048 维）切到本机
> Ollama（Qwen3-Embedding，4B → 2560 维 / 8B → 4096 维），检索链路不变：
> FTS5 + sqlite-vec → RRF → scope 过滤。

## 1. 一次性修复：第三方 GGUF 缺 `pooling_type`

**现象**

```bash
curl -s localhost:11434/api/embed -d '{"model":"dengcao/Qwen3-Embedding-4B:Q5_K_M","input":"x"}'
# 501 {"error":"This server does not support embeddings. Start it with `--embeddings`"}
```

`ollama serve --embeddings` 会报 `unknown flag`——那句提示是误导。真实原因：

| 检查项 | 结果 |
|---|---|
| `GET /api/tags` 里该模型的 `capabilities` | `["completion","tools","thinking"]`（没有 `embedding`） |
| GGUF 里的 `qwen3.pooling_type` | **不存在**（只有 `qwen3.embedding_length=2560`） |

Ollama 靠 `pooling_type` 判断"这是向量模型"，缺了它就把模型当对话模型，
`/api/embed` 与 `/v1/embeddings` 都直接 501。第三方转换脚本产出的
Qwen3-Embedding GGUF 经常缺这条元数据。

**修复**（不重新下载、不重新量化，只补一条 KV）

```bash
python scripts/patch_gguf_pooling.py \
  --src "D:/JZDSKit/llm_models/blobs/sha256-8b7c0cdf...e303efe" \
  --dst "D:/JZDSKit/llm_models/local/qwen3-embed-4b-pool3.gguf" \
  --arch qwen3 --pooling last

printf 'FROM D:/JZDSKit/llm_models/local/qwen3-embed-4b-pool3.gguf\n' > Modelfile
ollama create qwen3-embed-4b -f Modelfile
ollama show qwen3-embed-4b --modelfile | head -3   # 可选：确认
curl -s localhost:11434/api/show -d '{"model":"qwen3-embed-4b"}' | grep -o '"capabilities":[^]]*]'
# → ["tools","embedding"]
```

- 脚本只重写头部（多一条 `qwen3.pooling_type=3`），张量数据区整体复制，原文件不动；
- 需要约 2× 模型大小的磁盘（新 GGUF + Ollama blob 各一份，两者共享不了）；
- `--pooling last` 对应 Qwen3-Embedding 的最后一层池化；mean/cls 模型用 `mean` / `cls`；
- 输出向量已是 L2 单位向量（实测 `‖v‖=1.0000`），sqlite-vec 的 L2 距离排序等价于余弦。

### 1.1 4B / 8B 两个档位（同一套流程）

`dengcao/Qwen3-Embedding-8B:Q5_K_M` 与 4B 一样缺 `pooling_type`，处理方式完全相同，
只是模型名、维度、文件名不同：

| | 4B | 8B |
|---|---|---|
| 下载名 | `dengcao/Qwen3-Embedding-4B:Q5_K_M` | `dengcao/Qwen3-Embedding-8B:Q5_K_M` |
| `embedding_length` | 2560 | **4096** |
| 应用侧模型名 | `qwen3-embed-4b` | `qwen3-embed-8b` |
| 参数 / 体积 | 4B / 2.89 GB | 7.6B / 5.42 GB |
| 单次测试耗时 | ~23 ms | ~214 ms |
| 43 篇全量重索引 | ~40 s | ~6 min（含 3 本手册约 5490 块） |

```bash
# 8B：先按清单找到 model blob，再补元数据、建模型（与 4B 只差路径和名字）
python scripts/patch_gguf_pooling.py \
  --src "D:/JZDSKit/llm_models/blobs/sha256-14037f52..." \
  --dst "D:/JZDSKit/llm_models/local/qwen3-embed-8b-pool3.gguf" \
  --arch qwen3 --pooling last

printf 'FROM D:/JZDSKit/llm_models/local/qwen3-embed-8b-pool3.gguf\n' > Modelfile-8b
ollama create qwen3-embed-8b -f Modelfile-8b
curl -s localhost:11434/api/show -d '{"model":"qwen3-embed-8b"}' | grep -o '"capabilities":[^]]*]'
# → ["tools","embedding"]，model_info 里 qwen3.pooling_type=3、embedding_length=4096
```

清单里的 model blob 这样找（`size` 最大的那条就是）：

```bash
cat "D:/JZDSKit/llm_models/manifests-v2/ollama.com/dengcao/Qwen3-Embedding-8B/Q5_K_M" \
  | grep -o '"digest":"sha256:[a-f0-9]*"'     # → blobs/sha256-<hash>
```


> 顺带一个坑：`ollama create <名字>:local` 在某些版本会写出一条**不可解析**的清单
> （`ollama list` 看得到、`/api/show` 说 not found、`ollama rm` 也删不掉）。
> 遇到就删 `manifests-v2/ollama.com/library/<名字>/<tag>` 这一个清单文件，
> blob 是共享的，不会丢模型数据。

## 2. 应用侧配置

设置页「向量化模型」→ 运行方式选 **本地 Ollama**：

| 字段 | 值 |
|---|---|
| 服务地址 | `http://127.0.0.1:11434/v1`（只填 `http://127.0.0.1:11434` 也会自动补 `/v1`） |
| API Key | 本地模式不显示、不需要 |
| 模型名 | 下拉里只列 `capabilities` 含 `embedding` 的模型；不支持的灰掉并标注 |
| 向量维度 | 选中模型后按 `model_info.<arch>.embedding_length` 回填，可手改 |

「测试连接」会真实打一次 `embeddings.create`，返回耗时与实测维度并回填。

同一份配置也走接口：

```bash
curl -X PUT localhost:8686/api/config -H "Content-Type: application/json" -d '{
  "embedding": {"mode":"ollama","provider":"http://127.0.0.1:11434/v1",
                "model":"qwen3-embed-4b","dim":2560}}'
curl -X POST localhost:8686/api/config/test-embedding -d '{"mode":"ollama","model":"qwen3-embed-4b"}'
curl "localhost:8686/api/ollama/models"     # 本机模型清单 + 是否可向量化 + 维度
```

## 3. 实现要点

- `services/embedding.py`：唯一收敛提供方差异的地方——地址补 `/v1`、本机占位 Key、
  本机判定（127.0.0.1/localhost/::1）。本机不节流。云端仍是 10 条/批 + 3s 间隔 + 429 退避；
  本机 32 条/批、不重试（失败即真失败）。
- 批次节流口径变了以后，**换模型 = 一次全量重索引**：`chunk.model_id` 与配置不一致即重建；
  `chunk_vec` 声明维度不符时 `_ensure_vec_dim` 自愈重建（旧向量作废，由重索引补齐）。
- 重索引只覆盖**笔记**（`mode="full"` 扫 `note_file`），**PDF 手册要单独重建**：
  否则手册块仍是旧模型 / 旧维度，向量路对它们失效（关键词路照旧可用）。
- 实测：4B —— 43 篇笔记 1505 块约 40 秒（32 条/批，约 0.8s/批）；
  8B —— 同批笔记约 6 分钟；两者都远低于云端限频下的耗时。
- `GET /api/kb/stats.vector_model` 取**最近入索引**的块（原先是 `DISTINCT ... LIMIT 1`，
  会随机命中旧模型的残行）。

## 4. 排障

| 现象 | 原因 | 处理 |
|---|---|---|
| `does not support embeddings` / 501 | 模型缺 `pooling_type` | 按第 1 节补元数据后 `ollama create` |
| 下拉里模型是灰的、标「不支持向量化」 | 同上（`capabilities` 无 `embedding`） | 换模型或补元数据 |
| `test-embedding` 报 `Connection refused` | Ollama 没启动 / 端口不对 | 启动 Ollama；地址写 `127.0.0.1:11434/v1` |
| 保存后检索不到语义结果 | 还没重索引（旧向量维度不同被清空） | 设置页触发「重建全部索引」，或 `POST /api/kb/reindex {force,background}` |
| 维度提示不一致 | 配置维度 ≠ 索引维度 | 重索引；维度以「测试连接」实测为准 |
| `chunk` 有块但 `chunk_vec` 缺向量（手册） | 手册重建与笔记重索引并发时抢写向量表 | 单独重建该手册：`POST /api/manuals/<id>/rebuild`，完成后核对 `count(chunk)=count(chunk_vec)` |

> 一致性自查（应为 0）：
> ```sql
> SELECT count(*) FROM chunk c LEFT JOIN chunk_vec v ON v.rowid=c.id WHERE v.rowid IS NULL;
> ```
