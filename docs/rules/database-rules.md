# 数据库设计规则

| 项 | 内容 |
|---|---|
| 适用范围 | 本项目所有数据库设计、建表与修改 |
| 技术基线 | 单机 SQLite（WAL 模式）+ FTS5 全文扩展 + sqlite-vec 向量扩展；无独立数据库/缓存服务（见《02.整体架构设计.md》D3） |
| 强制性 | 数据库设计与修改必须遵守本规则；违反需先修订本规则并经项目所有者确认 |

---

## 1. 总则

1. 唯一数据库文件：`data/workbench.db`；禁止建立第二份业务数据库；
2. **Obsidian vault 是业务数据唯一真相源**（NFR-DATA-01）；数据库中与 vault 相关的表（笔记扫描缓存、切块索引）均为**可重建的派生数据**，必须支持"删库后依据 vault 全量重建"；
3. RAG 会话与配置**不可**由 vault 重建，属于必须备份保护的数据（OQ-10）；
4. 向量库、FTS 索引是切块表的派生结构，与主表同库同事务维护（见第 4 节）。

## 2. 命名与类型

1. 表名、列名一律 `snake_case`；表名用**单数**形式（`note_file`、`manual`、`chunk`）；
2. 主键：以业务路径为天然键的表用 `TEXT` 主键（如 `note_file.path`）；其余用 `INTEGER PRIMARY KEY`（SQLite 自动 rowid 别名，不显式 AUTOINCREMENT）；
3. 时间戳：`TEXT`，ISO 8601 UTC 格式（`YYYY-MM-DDTHH:MM:SSZ`），展示层负责转本地时区；
4. 业务日期（开始日期、最近更新等，与笔记 frontmatter 语义一致）：`TEXT`，`YYYY-MM-DD`；
5. 布尔：`INTEGER 0/1`；
6. 枚举：`TEXT` + `CHECK` 约束，禁止魔法数字；状态常量在 models 层统一定义；
7. JSON 列：列名以 `_json` 结尾，内容为合法 JSON 文本；JSON 仅用于"整体读写、无需按字段查询"的数据（如配置值、上下文快照），**需要关联或过滤的数据禁止塞进 JSON**。

## 3. 约束与关系

1. 连接时必须 `PRAGMA foreign_keys = ON`；关联关系显式声明外键；
2. **禁止使用 `ON DELETE CASCADE`**：一切删除（会话删除、手册删除清理切块等）由服务层在显式事务中按序执行，保证 FTS/向量同步与引用断链处理可审计；
3. 状态字段一律 `CHECK` 约束枚举；
4. 高频过滤列建索引；禁止盲目为所有列建索引。

## 4. 一致性（核心规则）

1. `chunk` 主表、`chunk_fts`（FTS5）、`chunk_vec`（sqlite-vec）三者**必须在同一事务内**写入、更新、删除——任何"主表写了、索引没写"的中间态都是缺陷；
2. FR-RAG-10 的三类变更同样单事务完成：删除手册 → 删切块 + 删 FTS + 删向量；内容更新 → 重建流程（见第 9 节）；移动/改名 → 仅更新路径标记失效；
3. 批量写入（增量索引、手册入库）使用事务分批提交（如每 100 块一提交），保证失败重试粒度可控且不长时间锁库。

## 5. 访问层

1. 全部 SQL 集中在 `backend/app/models/` 与 `backend/app/db.py`；**服务层禁止出现裸 SQL**；
2. 一律参数化查询，禁止字符串拼接 SQL（含表名/列名拼接）；
3. 连接策略：WAL 模式 + `busy_timeout`；单写多读；后台任务与 API 共用连接池（规模小，简单连接管理即可）。

## 6. 迁移

1. 使用 `schema_migrations(version INTEGER PRIMARY KEY, name TEXT, applied_at TEXT)` 记录版本；
2. 迁移脚本顺序编号（如 `m001_init.sql`），**已应用的迁移禁止修改**，变更一律新增迁移；
3. 应用启动时自动执行未应用迁移（幂等）。

## 7. 备份

1. 备份使用 SQLite 在线备份（`VACUUM INTO` 或 backup API），禁止直接拷贝热库文件（WAL 下不一致）；
2. 每日备份保留最近 7 份（OQ-10）；启动时距上次备份 >24h 补跑；
3. 备份记录写入 `backup_run` 表（时间、类型、文件、结果），作为"距上次备份"判断依据；
4. 存量整理（三期）的回滚备份复用备份服务，类型字段区分。

## 8. 安全

1. API Key 存于 `config` 表（本机文件），**禁止写入日志**、禁止经 API 回传前端（NFR-SEC-03）；
2. 界面/接口返回配置时，密钥类字段脱敏；
3. 数据库文件与备份文件均在 `data/` 下，随项目 `.gitignore` 排除。

## 9. 索引重建与 OQ-12 落地

1. 重建期间旧索引必须保持可用（OQ-12）：重建写入的新切块以 `status = 'rebuilding'` 入库，检索只命中 `status = 'ready'`；
2. 重建完成：单事务内"删除旧 ready 块（含 FTS/向量）→ 新块置 ready"；
3. 重建失败：单事务内"删除 rebuilding 块"，旧 ready 块不受影响；
4. embedding 模型变更（维度/模型 ID 变化）：全库向量不可用，必须全量重建；`chunk.model_id`、`chunk.dim` 记录生成模型，检索前校验与当前配置一致，不一致则提示重建（R4 缓解）。

## 10. FTS5 中文分词

1. 默认方案：**应用层 bigram（二字组）分词**——写入与查询前由服务层统一处理，FTS 表独立存储分词文本（非 external content 表）；
2. 最终方案以开发启动阶段 V2 spike（真实售后笔记命中率测试）结论为准；切换分词方案只需重建 FTS 表 + 数据迁移，不影响主表结构；
3. 型号/故障码（ASCII 连续串）保持原样不拆，保证精确命中（FR-RAG-16）。

## 11. 性能与规模

1. 规模基线：切块 ≤5 万、笔记 ≤50 篇、手册几十份——在此规模内**优先简单性**，不过度优化、不引入额外中间件；
2. 看板统计缓存（NFR-PERF-04）用进程内缓存实现，不入库；
3. KNN 查询的范围过滤（当前项目/品牌等）允许"向量召回后 SQL 过滤"的后过滤方式，规模内性能足够。

## 12. 三期表

1. 三期模块（终端会话、Git 仓库记录、存量整理批次/回滚）的表结构在**三期启动前补充设计**，本阶段不建表；
2. `schema_migrations` 机制支持届时平滑加表，无需变更既有表。

## 13. 现行表清单（本次交付范围）

| 分组 | 表 |
|---|---|
| 配置 | `config`、`brand` |
| vault 派生 | `note_file` |
